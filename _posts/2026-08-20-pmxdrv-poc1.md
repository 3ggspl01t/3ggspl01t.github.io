## Context

In the [previous post](https://3ggspl01t.github.io/posts/reconstruct-ioctl-input-structure/), we reconstructed the input structure expected by `pmxdrv.sys` for IOCTL `0x00222AB8`.

We now have a good idea of what the driver expects:

```text
IOCTL input
│
├── +0x00 ──► pointer to REQUEST
└── +0x08 ──► control/flag value

REQUEST
│
├── +0x00 ──► Size
├── +0x04 ──► PhysicalAddress
├── +0x0C ──► PageCount
└── +0x10 ──► MappedAddress
```

The next step was to put this reconstructed structure to the test. I wanted to see if I could actually get `pmxdrv.sys` to map a physical memory address from a user-mode PoC.

## What Does the PoC Do?

At this stage, the PoC is relatively simple and does not attempt to turn the primitive into a full exploit. Instead, the goal is to demonstrate that the physical-memory mapping functionality identified during the reverse engineering can be reached from user mode.

Before getting into the code, let's run through what the PoC does:

- [ ] Obtains device handle
- [ ] Builds input structure
- [ ] Requests a one-page mapping of physical address 0x100000
- [ ] Retrieves the returned mapped address
- [ ] Reads and saves the first 16 bytes from mapped address (confirming read primitive)
- [ ] Writes a 16-byte test pattern to mapped address
- [ ] Reads back and verifies the bytes written (confirming write primitive)
- [ ] Restores original contents to the mapped address

The PoC requests a one-page mapping of physical address 0x100000. If the driver returns a valid mapped address, the PoC reads the first 16 bytes and saves the original contents. It then writes a 16-byte test pattern to the mapped address, reads it back to verify the write, and finally restores the original bytes.

This gives us a relatively safe way to demonstrate both the read and write primitives.

## Building the Request

Let's start with the structures reconstructed in the previous post.

```cpp
typedef struct {
    DWORD  Size;             // +0x00, must be 24
    UINT64 PhysicalAddress;  // +0x04
    DWORD  PageCount;        // +0x0C
    UINT64 MappedAddress;    // +0x10, output
} REQUEST;

typedef struct {
    UINT64 Request;          // +0x00, points to REQUEST structure
    DWORD  Flag;             // +0x08, must be <= 63
    DWORD  Unknown;          // +0x0C
} INPUT_BUFFER;
```

The `REQUEST` structure contains the information needed by the driver:
- `Size` tells the driver the size of the structure.
- `PhysicalAddress` specifies the physical address to map.
- `PageCount` specifies how many pages to map.
- `MappedAddress` is where the driver stores the resulting mapping.

The outer `INPUT_BUFFER` is slightly different. Its first field is a pointer to the `REQUEST` structure rather than the structure itself.

The PoC initializes the request like this:

```cpp
REQUEST* request = (REQUEST*)VirtualAlloc(
        NULL,
        sizeof(*request),
        MEM_COMMIT | MEM_RESERVE,
        PAGE_READWRITE
    );

request->Size = sizeof(*request);
request->PhysicalAddress = TARGET_PHYSICAL_ADDRESS; // 0x100000ULL
request->PageCount = PAGE_COUNT; // 1
request->MappedAddress = 0;
```

And then points the outer structure at it:

```cpp
INPUT_BUFFER input;
input.Request = (UINT64)(uintptr_t)request;
input.Flag = 0;
input.Unknown = 0;
```

At this point, everything looked right. The next step was to send it to the driver.

## Sending the Request

The request is sent using the Windows `DeviceIoControl` API:

```cpp
DeviceIoControl(
    pmxdrvHandle,       // Handle to \\\\.\\PMXDRV
    IOCTL_MAP_PHYSICAL, // 0x00222AB8
    &input,             // Pointer to INPUT_BUFFER structure
    sizeof(input),
    NULL,
    0,
    NULL,
    NULL
);
```

The input to `DeviceIoControl()` is the `INPUT_BUFFER`, not the `REQUEST` structure directly. The driver receives the outer structure, follows the pointer stored at `+0x00`, and accesses the `REQUEST` structure from there. If everything goes according to plan, the driver writes the resulting mapping address into the `REQUEST` structure's `MappedAddress` field:

```cpp
UINT64 mappedAddress = request->MappedAddress;
```

I could then use this address to access the mapped physical memory. At least, that was the plan.

## PoC Kept BSODing

I compiled the PoC, loaded the driver and executed the PoC. Instead of returning a mapped address, Windows crashed.

SO, what is causing the crash?

## The Painful Lesson: Structure Packing

Looking at the structure definition again, the fields were definitely in the right order. But there was something I overlooked: **structure alignment**. On 64-bit builds, compilers automatically align `UINT64` fields on an 8-byte boundary by inserting padding inside structures so that 64-bit fields fall on 8-byte offsets.

Without specifying any explicit alignment, the structure ended up looking like this:

*`REQUEST` structure based on default alignment*
```text
+0x00  Size
+0x04  padding
+0x08  PhysicalAddress
+0x10  PageCount
+0x18  MappedAddress
```

But that is not what the driver expects. From reverse engineering, we know that the driver accesses the fields at:

*`REQUEST` structure expected by `pmxdrv.sys`*
```text
+0x00  Size
+0x04  PhysicalAddress
+0x0C  PageCount
+0x10  MappedAddress
```

The difference is subtle, but critical. The driver expects `PhysicalAddress` at `+0x04` but the compiler places it at `+0x08` based on default aligment. The driver reads an invalid address at `+0x04` and throws a BSOD. Painful lesson learnt.

## Fixing the Structure Packing

The solution was to override the compiler's default alignment behaviour using the `#pragma pack` directive:

```cpp
#pragma pack(push, 1)

typedef struct {
    DWORD  Size;             // +0x00, must be 24
    UINT64 PhysicalAddress;  // +0x04
    DWORD  PageCount;        // +0x0C
    UINT64 MappedAddress;    // +0x10, output
} REQUEST;

typedef struct {
    UINT64 Request;          // +0x00, points to REQUEST structure
    DWORD  Flag;             // +0x08, must be <= 63
    DWORD  Unknown;          // +0x0C
} INPUT_BUFFER;

#pragma pack(pop)
```

`#pragma pack(push, 1)` tells the compiler to use 1-byte alignment for the structures that follow, ensuring the fields are placed exactly at the offsets expected by the driver. `push` saves the current packing setting, while `pop` restores it afterwards. This limits the packing setting to the structures defined between the `push` and `pop` and does not affect other structures.

With the packing corrected, I rebuilt the PoC and ran it again. This time, things looked very different.

## Conclusion

The PoC successfully reproduced the physical-memory mapping path identified during reverse engineering. More importantly, it demonstrated that the returned mapping could be accessed from user mode for both reading and writing.

The key lesson for me was the importance of getting the structure layout exactly right. A four-byte padding difference was enough to turn an apparently correct PoC into a kernel crash.

With the structure layout problem out of the way, we now have a working PoC that demonstrates the physical-memory read/write primitive exposed through IOCTL `0x00222AB8`.

The next step is to expand this PoC into one that allows a normal user to escalate privileges to SYSTEM.
